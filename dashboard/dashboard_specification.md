# Looker Studio Dashboard Specification — Rewards Value Realization & Incrementality Lab

**Release status:** Build-ready configuration specification; the live Looker Studio report has not yet been created or independently validated.

## Dashboard contract

- **Report title:** Rewards Value Realization & Incrementality Lab
- **Required banner on every page:** `SYNTHETIC PORTFOLIO DATA — NOT STARBUCKS ACTUALS`
- **Date window:** January–June 2026; experiment post-period April–June 2026.
- **Primary estimand:** Treatment-minus-control difference in cumulative April–June contribution per member randomized on April 1, including members who later become inactive and all modeled costs.
- **Primary inference source:** Python `outputs/looker_studio_results.csv`, generated by `src/analyze_experiment.py` and loaded as BigQuery table `driiiportfolio.starbucks_rewards_lab_restart.looker_studio_results`. This source carries the exact Welch interval, p-value, run ID, and adjusted HC3 sensitivity estimate.
- **Trend and segment sources:** Governed BigQuery views created by `sql/03_build_analytics.sql`.
- **No blended data:** The views already aggregate at the intended grain. Do not blend event-level benefit rows with member-month rows.
- **Default interaction:** Cross-filtering OFF initially; use page-level filters and drill-downs only where documented. Avoid accidental cross-filtering that changes a KPI's population without making that change visible.

## Data sources to add in Looker Studio

Add the following BigQuery views from project `driiiportfolio`, dataset `starbucks_rewards_lab_restart`:

1. `vw_dashboard_monthly_arm_performance` — one row per month and randomized arm.
2. `vw_dashboard_experiment_arm_summary` — one row per randomized arm for the full experiment window.
3. `vw_dashboard_tier_arm_summary` — one row per tier and arm.
4. `vw_dashboard_channel_arm_summary` — one row per acquisition channel and arm.
5. `vw_dashboard_benefit_arm_summary` — one row per tier and arm; event-grain counts and post-period costs.
6. `vw_benefit_funnel` — one row per month, tier, and arm; monthly event-grain metrics.
7. `vw_experiment_member_outcomes` — member-grain outcomes; use only when an individual-member-level aggregate is necessary.

Add the uploaded table `looker_studio_results` for exact Python inference. Do not use an older output file or manually type the estimate into a chart. The `analysis_run_id` must match the current `outputs/experiment_results.json` before publication.

## Page 1 — Executive Overview

Purpose: answer what was tested, who was randomized, and what the primary estimate says without overstating the evidence.

### Scorecards

- Randomized members: `vw_dashboard_experiment_arm_summary`; metric `SUM(randomized_members)` with no dimension. Expected total: 18,866.
- Primary ITT estimate: `looker_studio_results`; filter `result_type = ITT_OUTCOME` AND `outcome = post_contribution`; metric `AVG(effect_estimate)`, currency, two decimals.
- 95% CI lower bound: same filter; `AVG(ci95_low)`, currency, two decimals.
- 95% CI upper bound: same filter; `AVG(ci95_high)`, currency, two decimals.

### Charts

1. **Monthly contribution per randomized member by arm** — line chart; source `vw_dashboard_monthly_arm_performance`; dimension `month_start`; metric `AVG(contribution_per_randomized_member)`; breakdown `assignment_group`; sort by `month_start` ascending. Filter to `period_phase = POST` only if the title says post-period; otherwise show all six months and annotate April as the intervention start.
2. **Monthly purchasing-member rate by arm** — line chart; same source/dimension/breakdown; metric `AVG(purchasing_member_rate)` formatted Percent. This is a monthly member-level rate, not cumulative six-month unique-member rate.
3. **Post-period contribution by tier and arm** — grouped bar chart; source `vw_dashboard_tier_arm_summary`; dimension `tier_at_launch`; breakdown `assignment_group`; metric `AVG(mean_post_contribution_per_member)`; descending by the overall tier average only if a stable sort field is available; otherwise sort tier in Green, Gold, Reserve order. Treat tier cuts as descriptive; no tier-specific causal claim without intervals/power analysis.

### Text panel

State: randomized assignment occurred April 1, 2026; primary outcome is cumulative April–June contribution/member; estimates are synthetic; primary analysis is ITT; benefit redemption is not itself causal evidence; this prototype does not evaluate the actual Starbucks Rewards redesign.

## Page 2 — Member Activity & Retention

Purpose: show activity/attrition patterns and how outcomes vary by acquisition channel without treating repeated monthly observations as unique members.

1. **Active-at-start rate by month and arm** — line chart; source `vw_dashboard_monthly_arm_performance`; dimension `month_start`; metric `AVG(active_at_start_rate)` formatted Percent; breakdown `assignment_group`; ascending date.
2. **Transactions per randomized member by month and arm** — line chart; same source; metric `AVG(transactions_per_randomized_member)`; breakdown `assignment_group`.
3. **Net sales per randomized member by month and arm** — line chart; same source; metric `AVG(net_sales_per_randomized_member)` formatted currency; breakdown `assignment_group`.
4. **Post-period contribution by acquisition channel and arm** — grouped bar chart; source `vw_dashboard_channel_arm_summary`; dimension `acquisition_channel`; breakdown `assignment_group`; metric `AVG(mean_post_contribution_per_member)`; tooltip includes `SUM(randomized_members)` only if displayed as a clearly labeled sample size.
5. **Member outcomes by tier** — table; source `vw_dashboard_tier_arm_summary`; dimensions `tier_at_launch`, `assignment_group`; metrics `SUM(randomized_members)`, `AVG(mean_post_contribution_per_member)`, `AVG(mean_post_transactions_per_member)`, `AVG(mean_post_net_sales_per_member)`, `AVG(post_purchaser_rate)`.

Do not sum monthly `active_at_start_members` or monthly distinct member counts to state six-month unique members. The panel intentionally keeps rows after attrition; inactive member-months remain in the randomized-member denominator and have zero activity.

## Page 3 — Benefit Operations & Economics

Purpose: distinguish eligibility, exposure, use, and cost. These are descriptive operational metrics.

1. **Eligible, exposed and exposed-and-used events by arm** — grouped bar chart; source `vw_dashboard_benefit_arm_summary`; dimension `assignment_group`; metrics `SUM(eligible_events)`, `SUM(exposed_events)`, `SUM(exposed_and_used_events)`. The bars compare event counts; they are not a causal effect estimate.
2. **Exposure per eligible event by tier and arm** — grouped bar chart; source `vw_dashboard_benefit_arm_summary`; dimension `tier_at_launch`; breakdown `assignment_group`; metric `AVG(exposure_per_eligible_event)` formatted Percent. This ratio is calculated at event grain and is not a member-level rate.
3. **Use per exposed event by tier and arm** — grouped bar chart; same source; metric `AVG(use_per_exposed_event)` formatted Percent. Control has zero exposed events, so this rate is NULL for control and must remain blank, not zero.
4. **Total benefit cost by tier and arm** — grouped bar chart; source `vw_dashboard_benefit_arm_summary`; dimension `tier_at_launch`; breakdown `assignment_group`; metric `SUM(benefit_cost_total)` formatted currency.
5. **Monthly benefit funnel table** — source `vw_benefit_funnel`; dimensions `month_start`, `tier_at_launch`, `assignment_group`; chart filter `assignment_group IN ('TREATMENT', 'CONTROL')`; metrics `SUM(eligible_events)`, `SUM(exposed_events)`, `SUM(exposed_and_used_events)`, `SUM(unexposed_used_events)`, `SUM(benefit_cost)`, and rates only when aggregated from event counts. If rates are recomputed in Looker Studio, use the calculated fields below and guard zero denominators.

### Calculated fields for benefit-event rates

Create these as chart-level or data-source calculated fields when the chart aggregates multiple rows. Their numerator and denominator are both event counts, so they are weighted correctly across month/tier groups.

- **Exposure per eligible event** (Number → Percent):
  ```text
  CASE
    WHEN SUM(eligible_events) = 0 THEN NULL
    ELSE SUM(exposed_events) / SUM(eligible_events)
  END
  ```
- **Exposed-and-used per exposed event** (Number → Percent):
  ```text
  CASE
    WHEN SUM(exposed_events) = 0 THEN NULL
    ELSE SUM(exposed_and_used_events) / SUM(exposed_events)
  END
  ```
- **All used events per eligible event** (Number → Percent):
  ```text
  CASE
    WHEN SUM(eligible_events) = 0 THEN NULL
    ELSE SUM(used_events_total_including_unexposed_organic_use) / SUM(eligible_events)
  END
  ```

Do not use `AVG(exposure_per_eligible_event)` or `AVG(use_per_exposed_event)` to roll up multiple source rows: that would give small and large denominators equal weight. In particular, the control arm's exposed-event denominator is zero; use-per-exposed must display blank/NULL, not 0%.

Add a visible note: “Benefit use is descriptive. Comparisons among redeemers and non-redeemers are not randomized causal estimates.” Cost metrics are from synthetic assumptions, not actual Starbucks program costs.

## Page 4 — Experiment Results & Decision

Purpose: show the primary randomized estimate, uncertainty, secondary outcomes, and adjusted sensitivity separately.

1. **Primary ITT result** — scorecards from `looker_studio_results`; filter `result_type = ITT_OUTCOME` AND `outcome = post_contribution`; display `effect_estimate`, `ci95_low`, `ci95_high`, `p_value_two_sided`, `n_treatment`, `n_control`. Use the exact Python output, not a Looker Studio approximation.
2. **Treatment/control arm means** — table; source `vw_dashboard_experiment_arm_summary`; dimension `assignment_group`; metrics `SUM(randomized_members)`, `AVG(mean_post_contribution_per_member)`, `AVG(mean_post_transactions_per_member)`, `AVG(mean_post_net_sales_per_member)`, `AVG(post_purchaser_rate)`, `AVG(mean_post_benefit_cost_per_member)`.
3. **Exploratory outcome estimates** — table; source `looker_studio_results`; filter `result_type = ITT_OUTCOME`; dimensions `outcome`, `description`; metrics `AVG(mean_treatment)`, `AVG(mean_control)`, `AVG(effect_estimate)`, `AVG(ci95_low)`, `AVG(ci95_high)`, `AVG(p_value_two_sided)`. Format each outcome deliberately: contribution and net sales as currency, transactions as decimal number, purchaser rate as Percent. If one chart cannot format by outcome type, split into separate tables by outcome.
4. **Adjusted sensitivity estimate** — scorecards from `looker_studio_results`; filter `result_type = ADJUSTED_SENSITIVITY`; metric `AVG(effect_estimate)`, `AVG(ci95_low)`, `AVG(ci95_high)`, plus `AVG(r_squared)` in a separate card if useful. Label “Adjusted HC3 sensitivity model — not the primary estimate.”
5. **Run provenance table** — source `looker_studio_results`; filter to `is_primary = TRUE`; dimensions `analysis_run_id`, `analysis_code_version`, `description`; metric `MAX(synthetic_data_only)` if a Boolean aggregation is needed, or display the synthetic disclaimer as static text. Confirm run ID matches the current analysis output before publishing.

Decision language must be conditional. Do not recommend scaling solely because a synthetic estimate is statistically significant. A real deployment decision would also require actual data, pre-registered guardrails, cost validation, power analysis, operational feasibility, and independent review.

## Global style settings

- Use a restrained neutral palette. Treatment and control colors must remain consistent across every page; avoid red/green semantics that imply good/bad by default.
- Canvas: widescreen layout; consistent left alignment, spacing, and chart titles.
- Page title at top, synthetic-data banner directly beneath it, then scorecards/charts.
- Currency: USD, 2 decimal places. Rates: Percent, 1 decimal place unless the primary estimate's interval needs 2. Counts: integer with thousands separators. Dates: `MMM YYYY` for chart axis labels where supported.
- Line charts: markers on, legend visible, month ascending, no smoothing that suggests unobserved observations. Use a vertical reference annotation for April only if the report editor supports a clear annotation; otherwise add a text note.
- Bar charts: zero baseline, data labels when legible, legend visible, no 3D effects. For grouped bars, keep treatment/control grouping and order consistent.
- Tables: totals off unless the total is meaningful at that table's grain; avoid totals on rows that contain per-member means or rates.
- Cross-filtering: off by default. If enabled for tier/channel exploration, visibly show that all affected charts have been filtered.
- Avoid blending data sources. Do not create a single chart that sums repeated monthly member counts and calls them unique members.
